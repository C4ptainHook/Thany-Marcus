# CLOUD-UPDATE — Day-2 updates for provisioned user clouds (in-place + blue-green) — Handoff Brief

Date: 2026-06-06
Status: **DESIGN — grilling complete, NOT yet implemented.** This brief records the decisions from the 2026-06-06 design session so they are not re-litigated. All forks resolved 2026-06-06 (Fork 5 → **B2 owner-anchor recovery**); the 2026-06-06 review also tightened Decisions 7 (apply-endpoint auth = elevated plugin token, blast-radius bounded by the host updater + monotonic) & 8 (quiesce-before-snapshot; dimension-change re-embed pre-cutover). **Implementation-ready.**

## The problem this solves

Once a user cloud is provisioned it is **immutable for life**: the `docker-compose.yml` is baked *inline* into the cloud-init template, `IMAGE_TAG` is pinned at `terraform apply`, the Qwen models are `ollama pull`'d once at first boot, and there is **no version concept, no update agent, and no portal→cloud control channel**. The only thing that self-updates is OS security patches via `unattended-upgrades`. So shipping a new model, image, schema, or compose topology today means **destroy + re-provision** — and that is *lossy*, because `sync never re-ingests` and there is no bulk re-ingest: a fresh cloud cannot rebuild the embeddings / entity graph / essences a user had. Today's reality is therefore "no in-place update **and** the nuclear option silently destroys derived state."

**Goal:** a user can apply any product update — code, sidecar, model (incl. the embedding model), schema, compose topology — to their *running* cloud, **user-initiated**, **without data loss**, and **without the portal ever reaching into the running cloud**.

## The non-negotiable framing (settled first, everything hangs off it)

**"The portal must not trespass on the user cloud."** Trespass = the portal reaching **into the running cloud's data/control plane** (SSH, an authenticated `/admin/*` call, a standing credential that can mutate the app). It is **NOT** trespass for the portal to perform **DO-level lifecycle under the user's OAuth grant** (create/snapshot/attach/destroy droplets and volumes) — the portal already does exactly this when it provisions and destroys a cloud, it acts on DO not on the app, and **it never reads the cloud's data** (DO does snapshots server-side; no plaintext crosses the portal). The user explicitly accepted this line on 2026-06-06.

> Consequence: **updates are pull / owner-mediated.** The portal can never *push* an update into a cloud. It can *record consent* and *orchestrate DO lifecycle*; the cloud either pulls, or the owner's agent (plugin) carries the instruction in.

## Decisions resolved in the 2026-06-06 grilling

Recorded so the next reader does not re-litigate.

1. **Trust posture → zero live operational credential, true by construction.** Started as a "bounded promise" but landed stronger via Fork 4: Phase 0 does (a) move `/admin/settings` off the bootstrap token (different rightful caller = the owner, different lifetime), (b) make the bootstrap token **single-use** (consumed at first plugin-token push, then inert; transient saga state only, never a permanent column), (c) move plugin-token **rotation** to **owner-carried** (portal mints, plugin fetches and presents to its own cloud), and then (d) **delete `EncryptedCloudAdminToken`**. After that the portal stores no cloud credential and never opens a socket to a running cloud. **Thesis wording: "the portal holds NO live operational credential to a running cloud — enforced by the absence of the credential, not by restraint; the only provisioning-time secret is single-use and inert after birth."** Recovery from total token loss is **owner-anchored** too (Fork 5 / B2 — a show-once recovery code the cloud only hashes), so even re-establishing access never hands the portal a standing key over the cloud. (Avoid the over-claim "the portal cannot reach the cloud at all" — it still does DO-level lifecycle under OAuth.)
2. **No cryptographic signing — for now.** The signing private key would live in CI, so signing protects against *nothing* in the catastrophic case (CI compromise signs a malicious manifest too); it only covers manifest-tamper-independent-of-CI. Host the release feed where **write-access == CI-access** and that residual collapses to zero. Integrity instead = HTTPS + **digest-pinning** + a **`ghcr.io/c4ptainhook/*` namespace allowlist baked into the updater** + **monotonic versions** (refuse any version ≤ current). Under those, a tampered bundle can only name real images in your namespace, forward-only — no code injection, no downgrade. **Documented deferral trigger:** signing re-earns its keep only when the signing key can live *outside* CI's trust boundary (offline/hardware key, separate signer role) — post-thesis.
3. **Updates are user-triggered only.** One consent class. The **application stack never self-updates.** The single deliberate exception is `unattended-upgrades` (OS/apt security patches on the host) — kept, and scoped explicitly to the host, not the stack.
4. **Plugin-driven.** Detection = the plugin compares "what version is my cloud running" (asked of the cloud — it reports its own version, stays passive) against "latest version + bundle" read from the **release feed**. Only *apply* is user-gated.
5. **The "manifest" is a portal-served, public-read RELEASE FEED, read by the PLUGIN — not polled by the cloud.** It carries version + bundle metadata (non-secret, same for every user). CI registers each release to the portal (the portal is the version authority). The cloud never reads it.
6. **Tiered apply, decided by what the migration touches** (the governing principle, not a vibe):
   - **only recomputable derived state** (embeddings, hashes) — *including a same-dimension embedding-model swap* → **in-place**. Rollback-safe because any version rebuilds it from preserved `BodyInput`/`BodyOutput`; a rolled-back image just re-embeds with its own model+tag. Source text is never at risk.
   - **structural** (`vector(256)`→`vector(N)`, dropped columns) **or mutates irreplaceable source** → **blue-green** (pristine old copy = safe rollback). **Expand-contract migration discipline is therefore NOT required** — the migration runs on a disposable copy.
   - **stale-but-valid derived state** (synthesis/extraction LLM swap → essences, entity graph) → in-place, **lazy/opt-in re-derive** (old output still renders).
7. **In-place mechanics — plugin↔cloud, portal not in the loop.** The plugin **carries the bundle** (rendered compose + image digests + model tags + env-overlay it read from the release feed) to its own cloud. **Auth: the apply endpoint is gated by `RequirePluginAuthFilter` — the plugin (data-plane) token** — because Phase 0 deletes the only other inbound auth (the cloud-admin token); there is no separate "owner-auth channel." **This elevates the plugin token**: a pure data-plane credential now also *triggers* a system update (image pull + `compose up` + restart) — the one data-plane→control-plane crossing in the design. Make it safe **by construction, not by trust**: the HTTP endpoint only *relays* the bundle to the **host-side updater**, which is the policy enforcer and verifies **namespace allowlist + image digest + monotonic version** before acting — so it doesn't matter who sent the bundle (a stolen token can't inject or redirect images). **Blast radius of a stolen plugin token:** it already owns the data plane (read/write the user's notes), so the *incremental* power is only "request an update," bounded to **at most one forced jump to current-latest** — allowlist+digest block injection, **monotonic blocks downgrade AND blocks re-applying the same version (so no restart-loop DoS — repeat calls are no-ops)**, and the owner can `RevokedAt` the token. *Optional hardening:* add a capability bit to `PluginToken` (today an opaque hashed secret with `Id`+`Label`, no scopes) so only a designated token may call apply, preserving a pure data-plane-only token class. **The cloud still needs NO portal channel, inbound or outbound.**
8. **Blue-green mechanics — plugin triggers, portal executes.** Plugin sees `strategy: blue-green` → **deep-link redirect to the portal** (carrying `cloudId` + target `vX`) → portal **signs in if the session expired** (return-URL survives) → **confirm screen** ("re-provisions your cloud, ~X min, data carried, old kept until verified") → portal SagaWorker runs the saga via the user's DO OAuth → **SSE progress** + the toast/favicon notification layer. The saga is **quiesce the plugin (stop new submissions, drain in-flight to a durable ACK) → snapshot the data volume → new droplet at vX → migrate the COPY → verify → reserved-IP cutover → post-cutover health gate → destroy old**. **Ordering is load-bearing: quiesce BEFORE snapshot.** If you snapshot first while the old cloud keeps serving, any capture it ACKs in the snapshot→cutover window lands only on the old volume *and* is dropped from the plugin's pending-intent queue (ACKed = done) → it is neither in the snapshot nor replayed → **silently lost**. After quiesce, the snapshot is complete and the pending queue holds only post-quiesce captures, which replay after cutover. (In-flight *processing* jobs live in Postgres on the data volume → snapshotted and resumed on the new cloud.) The original droplet+volume stay **pristine** until the post-cutover gate passes (= safe rollback). Domain unchanged (IP reassign), so the plugin **reconnects transparently** and **replays the queue** — the user sees a pause, not a reconfiguration. **Pre-check DO capacity** (via the OAuth token) before starting, fail gracefully if a transient second droplet won't fit. **Dimension-change embeds:** run the re-embed sweep on the new droplet *during the pre-cutover verify phase* (the old cloud serves reads in the old space meanwhile), so cutover lands on a **complete** new-space corpus and there is **no post-cutover degraded window** — only the *in-place same-dim* path uses the Phase-5 "re-indexing" pause.
9. **`.env` is never replaced — only the overlay is merged.** It holds per-cloud secrets generated at provision (`POSTGRES_PASSWORD`, `JWT_SIGNING_KEY`, the admin token). The update merges `.env.overlay` (non-secret knobs) over it; secrets untouched.
10. **Dumb updater, fat bundle.** All intelligence lives in the CI-rendered bundle (a fully-rendered compose); the on-box updater is a tiny verify→write→`compose pull`→`up -d`→health-gate→rollback loop that essentially never changes. This is what lets the compose stop being frozen-inline-forever without creating a "who updates the updater" bootstrap trap.
11. **No cloud-held DO token.** Rejected: a popped cloud could then spin up droplets on the user's DO account. DO lifecycle stays portal-side only.

## Does NOT ship / out of scope

- Cryptographic manifest signing (deferred — Decision 2; documented re-trigger).
- Background / automatic stack updates (Decision 3 — user-triggered only).
- Portal-imposed per-cloud version *targeting* / canary cohorts. The portal records the **owner's consent** per cloud; it does not decide what a cloud runs. (The hash-cohort canary idea was discussed and dropped in favor of plugin-driven per-user consent.)
- **Host-layer in-place updates** (nginx site, systemd units, **the updater itself**) — **re-provision only.** The updater stays dumb + near-frozen; "the updater needs changing" is the one case that means re-provision.
- A cloud→portal steady-state heartbeat (the cloud-polls-portal delivery option was rejected in favor of plugin-carries-bundle).
- Expand-contract migration discipline (obviated by blue-green for structural migrations — Decision 6).

## Resolved forks (2026-06-06)

1. **In-place re-index gate (mixed-space window) → HARD PAUSE on an explicit flag.** The cross-space window only exists during a (rare, user-initiated) embedding-model swap; graceful per-note degradation would return *silently incomplete* results (looks like a real "nothing related" answer), which is worse than an honest pause. So: a `reindex_in_progress` flag set by the model-swap migration and cleared when the re-embed sweep drains (`COUNT(embedding IS NULL) == 0`); related-notes shows a **"re-indexing" state** (not empty) while set. **Normal per-note re-embeds (edit/template) never trip it** — they produce same-space vectors. The per-note `embed_config` column / graceful-degradation option is deferred unless real re-index times prove painful.
2. **Blue-green old-droplet disposal → DESTROY ON VERIFIED CUTOVER, RETAIN SNAPSHOT 7 DAYS.** (Refines the earlier "keep stopped N days" rec: **DO bills powered-off droplets at full rate** — resources stay reserved until destroyed — whereas a volume snapshot is ~$0.06/GiB/mo.) Split by failure timing: **(mandatory, minutes)** keep old alive until the new droplet passes a *post-cutover* health/smoke gate; on failure reassign the IP back → old resumes → abort. **(grace, days)** once verified, destroy the old droplet but **keep the pre-migration volume snapshot for 7 days** as the catastrophic-rollback artifact (provision-from-snapshot; post-cutover writes are lost but the vault + pending-intent queue re-push them); GC the snapshot after.
3. **Cutover networking → RESERVED IP NOW; RE-ISSUE CERT AFTER REASSIGN.** Take a **DO Reserved IP** (seconds-fast reassign, no DNS propagation; region-scoped — fine, blue-green is same-region; free while attached). Provisioning change: allocate it, point the domain A-record at it permanently, bind the droplet. **Cert:** build+verify new on its ephemeral IP → reassign reserved IP old→new → new runs `certbot --nginx` (HTTP-01 works once the domain resolves to it). The seconds-long issuance gap falls **inside the announced freeze window** (plugin paused, not hitting HTTPS) → effectively invisible. DNS-01 pre-issue (gap-free) is the documented upgrade if that gap ever matters; skip it now (adds a DO-DNS-token moving part).

## Resolved fork 4 (2026-06-06)

4. **Delete `EncryptedCloudAdminToken`.** Once plugin-token rotation is owner-carried, the column has no caller — keep-dormant would leave a purposeless standing credential (pure liability), so drop it. **Implementation order matters: this is the LAST step of Phase 0, gated on (c) owner-carried rotation being live** — deleting it before that breaks `RetryPluginTokenEndpoint` (the portal still needs to reach the cloud to re-issue). The single-use bootstrap token, if the provisioning saga needs it for durability, lives only in **ephemeral saga state purged on completion** — never a permanent column. **Net effect: the portal holds NO live operational credential to a running cloud — true by construction, not by promise.** Thesis claim strengthens accordingly (see Decision 1).

## Resolved fork 5 (2026-06-06) — owner-anchor recovery (B2)

The hole: plugin tokens are **opaque secrets, SHA256-hashed and stored on the cloud** (`PluginToken.TokenHash`, matched by `PluginTokenAuthenticator`; `Id`+`Label`, no scopes), today (re)established by the portal via the admin channel that **Phase 0 deletes**. Rotation is *new-via-old*; the single-use bootstrap dies at birth. So after **total** token loss the running cloud had **no trust anchor** → unrecoverable without re-provisioning a healthy droplet.

**Chosen: B2 (owner-anchor).** The recovery anchor is held by the **owner**, not the portal — consistent with deleting `EncryptedCloudAdminToken`. (B1 — bake a portal public key, verify portal-signed recovery assertions — was rejected: a portal signing-key compromise could mint data-plane access into *any* cloud, re-introducing exactly the portal-credential-over-the-cloud we just removed.)

Mechanism:
- **Provision:** the cloud generates a high-entropy **recovery code** (like its other `openssl rand` secrets) and stores **only its hash** (`recovery_anchor_hash`), kept for the cloud's life. This is the durable owner trust anchor — distinct from the single-use bootstrap token.
- **Show-once delivery, portal never sees it:** the plaintext is returned to the owner **once via the plugin** (cloud→plugin, on the first authenticated handshake), displayed as "save this — it is the only way to recover if you lose this device." The portal is not in this path.
- **Recovery endpoint (cloud, `AllowAnonymous`, rate-limited):** a fresh-install plugin (no token) presents the code; the cloud verifies `FixedTimeEquals(hash(presented), recovery_anchor_hash)`, then **mints + returns a new `PluginToken`** and **rotates the recovery code** (re-show-once, since it just transited). Must be brute-force-hardened — high-entropy code + throttle/lockout, since the code is the *only* gate (no token present). Optionally offer "revoke other tokens" for the lost-device case.
- **Address discovery:** the portal MAY tell a fresh-install plugin its cloud's *address* (not a credential — just where to recover to); the user can also enter the domain manually.

*Concession (inherent to B2):* lose the token **and** the recovery code → re-provision. So the show-once UX must make saving the code prominent (Emergency-Kit-style). Deliberate trade for keeping the portal credential-free.

## Scope (logical phases)

### Phase 0 — Trust-boundary hardening (prerequisite; makes "no trespass" true enough to defend)
- Split `/admin/settings` off the bootstrap token onto owner auth.
- Make the bootstrap token single-use (cloud invalidates after first plugin-token push).
- Move plugin-token **rotation** to owner-carried (portal mints → plugin fetches → plugin presents to its own cloud); the portal stops calling the cloud.
- **Last:** drop the `EncryptedCloudAdminToken` column (migration) — only after owner-carried rotation is live, or you break `RetryPluginTokenEndpoint`. Portal now holds no cloud credential.
- **Owner-anchor recovery (Fork 5 / B2)** — replaces the deleted admin-channel recovery: provision generates a hashed show-once recovery code (`recovery_anchor_hash`), delivered once to the owner via the plugin (never the portal); a rate-limited `AllowAnonymous` cloud recovery endpoint trades a valid code for a fresh `PluginToken` and rotates the code. This is the cloud's durable owner trust anchor — without it, total token loss is unrecoverable.

### Phase 1 — Release feed + bundle (portal = version authority)
- CI registers each release to the portal: version, rendered `docker-compose.yml`, image **digests**, model tags, `strategy: in-place | blue-green`, `schema.min_from`. Serve a **public-read release feed** (write-access == CI-access).
- Cloud exposes a trivial "what version am I running" read (the plugin's other half of detection).

### Phase 2 — In-place updater on the cloud (dumb apply loop)
- Host systemd unit + tiny script: verify bundle (allowlist + digest + monotonic) → **merge** `.env.overlay` (never replace `.env`) → `ollama pull` new tags (old keeps serving) → `docker compose pull` → `up -d` (API restart runs `MigrateAsync()`) → health-gate `/admin/health` + `/health/ready` → commit (`current_version`) or roll back (re-`up` `previous/` digests). State (`current_version`, `previous/`) on `/mnt/thany-data`.
- **Stop baking compose inline-forever**: the updater fetches/writes the rendered compose. (Cross-cutting with provisioning.)
- **Enforce `schema.min_from`** (registered in Phase 1): the updater refuses in-place if `current_version < schema.min_from` (too far behind to apply safely) and **routes to blue-green instead** — its `MigrateAsync()` chains the full migration set on the copy. The **rollback re-`up` of `previous/` is an internal restore and is EXEMPT from the monotonic gate** (it intentionally goes to a lower version); don't let a "fix" make rollback honor monotonic.

### Phase 3 — Plugin update UX (the trigger surface)
- Detect (compare cloud's version vs release feed); show "vX available" + strategy + cost ("re-index ~X min" / "re-provision ~X min").
- In-place: carry the bundle to the cloud over the owner-auth channel; show progress/status.
- Blue-green: deep-link redirect to portal; show "updating," **hold + replay** the pending-intent queue; reconnect transparently post-cutover.

### Phase 4 — Blue-green saga (portal SagaWorker + DO OAuth)
- New saga kind (`Update`/`Migrate`): DO-capacity pre-check → **quiesce plugin (drain to durable ACK)** → snapshot data volume → new droplet at vX (reuse provisioning machinery) → migrate the COPY (its `MigrateAsync()` runs on the copy) → verify/health → **reserved-IP cutover** → **post-cutover** health/smoke gate (fail → reassign IP back to old → abort) → destroy old → **retain pre-migration snapshot 7 days, then GC** (per resolved Fork 2). SSE progress; reuse `Create`-saga auth.
- Provisioning change: allocate a **Reserved IP**, point the domain A-record at it permanently, bind the droplet; cert re-issues on the new droplet immediately after reassign (per resolved Fork 3).

### Phase 5 — Embedding re-index gate
- The mixed-space gate: `reindex_in_progress` flag → hard-pause related-notes with a "re-indexing" state, cleared when the sweep drains (per resolved Fork 1). Also: an embedding-model swap = new API image (new model + bumped `EmbedConfigTag` + a null-embeddings migration like `ReembedVaultClsPooling`) → in-place re-embed from stored bodies → re-run auto-calibration for the new space. Dimension change instead rides Phase 4 (blue-green, clean new-dim DB).

## One-paragraph summary for the impatient

Updates are **user-initiated** and **plugin-driven**. The portal is the **version authority** (public-read release feed) and the **DO-lifecycle executor**, but **never reaches into a running cloud**. **In-place** (code, sidecars, same-dim model swap, additive schema, anything touching only recomputable derived state): the **plugin carries a digest-pinned, allowlist-verified bundle** to its own cloud, which applies it and self-rolls-back on health failure — portal untouched. **Blue-green** (structural/destructive migration): the plugin redirects the user to the **portal**, which **snapshots → provisions a new droplet → migrates the copy → cuts over a reserved IP → destroys the old**, keeping the original pristine for safe rollback and reusing the existing provisioning saga. No signing (digest + allowlist + monotonic versions suffice while the key would live in CI). The embedding "monster" is already mostly solved in-place (`BodyInput`/`BodyOutput` + `EmbedConfigTag` re-embed); blue-green's real job is narrow — rollback-safe structural migrations.
